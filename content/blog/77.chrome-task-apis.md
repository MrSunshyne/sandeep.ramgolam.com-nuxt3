# The Task APIs: Chrome's Built-in AI You Can Use Today

There's a family of AI APIs sitting in Chrome right now that most web developers haven't touched. No SDK, no API key, no per-token bill, and nothing leaves the user's machine. You call `Summarizer.create()` in the console and the browser summarizes text for you, locally.

They're called the **task APIs** — small, purpose-built APIs for one job each — and three of them have been stable since Chrome 138: **Summarizer**, **Translator** and **Language Detector**. This post is an entry-level tour: what they are, the one pattern they all share, and what to honestly expect before you ship one.

If you read my [WebMCP post](/blog/webmcp-in-the-browser), this is the same story from another angle: the browser itself is becoming an AI runtime. WebMCP is how agents talk to your site; the task APIs are how your site does AI things itself.

## What "built-in" actually means

The model belongs to the **browser**, not to your page. Chrome downloads it once (the shared foundation model is around 4 GB — Google's docs describe it as Gemini Nano), keeps it on the machine, and every website shares it. Your JavaScript talks to a global object like `Summarizer` or `Translator`, and inference runs on the user's own hardware.

That flips the usual economics of AI features:

- **Privacy** — the text being summarized or translated never leaves the device.
- **Offline** — once the model is downloaded, everything works with Wi-Fi off.
- **Cost** — there is no server and no metered API in the loop. Zero.

The Translator and Language Detector don't even use the big model — each downloads its own small task-specific pack (one per language pair for translation), so they work on machines that can't run the 4 GB model.

## The one pattern to learn

Every API in the family has the same shape, so learning one is learning all of them. There are four availability states — `unavailable`, `downloadable`, `downloading` and `available` — and a `create()` call that can report download progress:

```js
// 1. Ask if the API can work here
const availability = await Summarizer.availability();

if (availability !== 'unavailable') {
  // 2. Create a session — this may trigger the one-time model download,
  //    so it has to happen after a user gesture (a click), not on page load
  const summarizer = await Summarizer.create({
    type: 'key-points',
    format: 'markdown',
    length: 'medium',
    monitor(m) {
      m.addEventListener('downloadprogress', (e) => {
        console.log(`Downloaded ${Math.round(e.loaded * 100)}%`);
      });
    },
  });

  // 3. Use it
  const summary = await summarizer.summarize(longArticleText);
}
```

Two details worth internalising early:

- A `create()` that needs to download a model **requires user activation**. Wire it to a button, show the progress, and the download UX becomes part of your feature instead of a mystery spinner.
- Sessions hold real resources on-device. Create, use, `destroy()` — don't hoard them.

## The stable trio

**Summarizer** gives you four summary types from the same input: `headline`, `teaser`, `tldr` and `key-points`, each in `short`/`medium`/`long`. Output can stream in as it generates, which feels great in a UI.

**Language Detector** returns candidate languages ranked by confidence:

```js
const detector = await LanguageDetector.create();
const results = await detector.detect('Hallo und herzlich willkommen!');
// [{ detectedLanguage: 'de', confidence: 0.99 }, ...]
```

**Translator** works per language pair, and chains naturally with the detector — detect first, then translate:

```js
const translator = await Translator.create({
  sourceLanguage: 'de',
  targetLanguage: 'en',
});
await translator.translate('Hallo und herzlich willkommen!');
```

Japan runs comment moderation on-device with these APIs, and Trip.com generates personalized travel summaries with them.

## The trio in limbo

There are three more — **Writer** (drafts text from a brief, with tone and length options), **Rewriter** (shifts tone: `more-formal` / `more-casual`) and **Proofreader** (returns corrections with exact character ranges, so you can highlight them in place).

Here's the honest part, as of Chrome 149 (July 2026): their origin trials have **ended** — Writer and Rewriter at Chrome 148, Proofreader at 145 — and none of them has graduated to stable yet. They're early enough that they don't even have [web-features](https://github.com/web-platform-dx/web-features) entries, so no Baseline banners for these three. On today's stable Chrome the globals simply don't exist, and upgrading Chrome makes them *disappear*, not appear. You can still try them behind flags (`chrome://flags`, search "gemini nano"), but don't build a product feature on them until they graduate. I'd watch the Chrome 150 release notes.

This is also your periodic reminder that the whole family is a Chrome (and Edge) thing, incubated in a W3C Community Group — it's not a cross-browser standard. ## Treat AI capability like any other browser feature

The four availability states are the whole progressive-enhancement story. `unavailable` isn't an error — it's a signal to show your non-AI fallback, the same way you'd treat a missing CSS feature. A "summarize this article" button that only appears when `availability()` says it can work is a *better* feature than one that breaks in Firefox.

The hardware bar is real and worth knowing before you commit: the foundation-model APIs want roughly **22 GB of free disk** and either a GPU with more than 4 GB of VRAM or the newer CPU path (16 GB RAM, 4 cores). Desktop only — no mobile Chrome. Google's answer to that gap, announced at I/O 2026, is **Gemma 197M**, an "ultra-efficient expert model" that can transparently back the task APIs on far more modest devices. The API you write against stays the same; the browser picks the brain.
